# 硬件与 API 知识策略

在主路由目录内，用目录来源记录和 API Top-N 精核可见代码核心。主目录可来自平台库，也可来自彼此隔离的 `custom:*` 自建库。

- 比较代码的数据形态、计算、访存、依赖和调用边界，与 API 记录的语义、输入输出、生命周期及 `runtime_verification`。Top-N 是候选，不是证明。
- 只使用当前 `primary_unit_id` 对应目录的记录。不得把 `custom:*` 改写、合并或悄悄替换为同名 NPU/GPU/DSP/媒体平台目录。
- 先给出最小作用域的语义匹配，再把设备能力、格式、搬运、同步、小批量开销和收益列为验证项。
- 主目录不相容时明确建议重新路由；某个 API 不相容时可在同一目录重选。没有记录时不编造具体 API。
- 自建记录只证明源码中的静态合同候选。公开性、调用权限、设备支持、功能等价和性能收益仍须独立验证。
- 同时评估 SIMD 与 CPU 并行：说明数据精度、任务切分、依赖、共享状态和粒度。
- `target_platform_profile` 不是 device probe。严格使用 `allowed_evidence_ids`，并生成契约要求的 `opportunities[]` 和对象形式 `analysis_scope`。
