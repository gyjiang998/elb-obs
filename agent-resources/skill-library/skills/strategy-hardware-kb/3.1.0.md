# 硬件与 API 知识策略

在主路由单元内，用硬件能力卡和 API Top-N 精核可见代码核心。

- 比较代码的数据形态、计算、访存、依赖和调用边界，与 API 记录的语义、输入输出、生命周期及 runtime_verification。Top-N 是候选，不是证明。
- 先给出最小作用域的语义匹配，再把设备能力、格式、搬运、同步、小批量开销和收益列为验证项。
- 主单元不相容时明确建议重新路由；某个 API 不相容时可在同一单元重选。没有记录时不编造具体 API。
- 同时评估 SIMD 与 CPU 并行：说明数据精度、任务切分、依赖、共享状态和粒度。
- target_platform_profile 不是 device probe；只能依据 context record 描述 OpenHarmony/Kirin 相关接口候选，不能推断当前芯片实现与可用性。
- 严格使用 allowed_evidence_ids，并严格生成 output_contract 要求的 `opportunities[]` 和对象形式 `analysis_scope`。
