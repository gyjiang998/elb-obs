# BuildItem 并行建模

## 目的

将实际场景负载转为可计算的依赖图，联动线程、服务、核类型与频率，回答怎样并行、如何放核、预计收益多少。

## 方法

1. 从页面 `parallel_modeling` 上下文获取数据集、目标帧和性能目标，通过 `parallel_modeling_catalog` 读取硬件画像、离线包及搜索空间。使用 `parallel_modeling_import_dataset` 导入 `builtin_id="gallery-edit-pmu-20261014"`、`capture_run_id/step_id`、`trace_text`，或 `parsed` 对象。原始 PMU 需同时提供 `pmu_text` 与真实 `pmu_metadata`；可指定 `target_tid/target_vsync_id`。新数据需选择适用的 `hardware_profile_id` 才能搜索，未选时仍可测量分析。步骤包络不能替代真实 UI callback。
2. 调用 `parallel_modeling_analyze(dataset_id)`，用 `parallel_job_read` 跟踪任务；通过 `parallel_modeling_read_analysis` 读取主线程前后段、BuildItem、同步服务、运行/等待账本和负载特征。依据数据覆盖解释可建模部分与补充采集机会。
3. 结合 `replay_gate.passed` 评估基线回放一致性，以 `candidate_ids` 选择条件并行组件。采用 `preserve_observed` 保留组件内顺序、同步请求与返回、未并行工作和服务争用；在组件线程安全、公共 fork 输入就绪、公共 join 后消费结果的明确假设下仿真。应用 `gallery-native-transfer-v1` 原生代理迁移包，并结合其 `legacy_compat` 校准状态说明预测的适用范围。
4. 调用 `parallel_modeling_search(search)`，设置 `analysis_id/model_package_id/candidate_ids/objective/space`。`minimum_latency` 目标最短耗时；`minimum_frequency_with_budget` 在 `budget_ms` 内按活动域最大归一化 OPP、归一化 OPP 和、核槽数及延迟排序。`space` 使用 `available_core_group_ids`（big/middle/small）、`main_core_group_id`、`worker_counts`、`main_participation`、`frequency_policy`（all_opps/max_opps），可用 `frequencies_khz` 限定频点；0 worker 需显式加入才能包含串行候选。同核组共享 OPP，worker 不混合核组。`robustness=true` 复核 18 个声明情景，不能解释为置信区间。
5. 使用 `parallel_job_read` 与 `parallel_modeling_read_search` 读取数值仿真结果，对比推荐配置、次优候选、关键路径变化、主线程参与、核频和资源时间。结合模型校准来源、覆盖范围与并行前提解释结果。

## 交付

推荐 worker 数、主线程参与方式、核组与频率、预测耗时及相对实测基线的收益、搜索覆盖和适用条件。频率字段是 kHz；应用 / 服务 core-ms 是资源占用，不是能耗。PMU 的上下界和可用性用于特征展示，generic cache misses 不等价 DRAM bytes。分别标明 measured 与 conditional_prediction；86.940 ms / vsync 60209 和历史 90.409 ms 是不同样本。图中实线表示顺序或依赖，虚线服务归属不是额外依赖。失败时报告真实质量 / 适用域 / 预算原因，支持用户调整约束后继续寻优。
