# 应用执行流程重建

加载 `code-context-retrieval`。`source_scopes` 是本轮全部代码仓范围，每项绑定独立源码快照与 ready 底图；分别查询后再跨仓串联。语义图用于缩小范围，真实源码用于确认，平台工具负责工件、投影和校验。

## 完整操作候选

1. 把用户目标整理为初始状态、1～N 个有序用户动作、用户可观察的最终结果以及包含/排除边界。候选覆盖完整旅程；单个函数、接口、回调或内部步骤只是旅程中的实现证据。
2. 对每个 source scope 用 `code_graph_get` 确认 ready 底图，以 `code_graph_query_knowledge` 做有界查询，再回读入口、跨模块转发和完成边界源码。静态调用候选只作导航，不冒充运行事实。
3. 为每个用户动作生成 `action_coverage`：`mapped` 记录关联仓和源码摘要，`partial` 或 `unmapped` 记录缺口与疑似缺失模块。它用于告诉用户还应添加哪个仓，而不是用猜测补齐链路。
4. 候选数量不固定为 3；仅在入口、操作模式、完成语义或范围解释确实不同时拆分。每个候选提交 `operation_scope="complete_user_operation"`、边界理由、有序 `user_actions`、`action_coverage`、高层 `semantic_outline`、参与者及已核对 entry/exit。跨仓边界在 entry/exit 中写 `source_connector_id`。
5. 调用 `application_flow_publish_candidates` 时原样提交全部 `source_scopes`。修订时读取父 discovery，传 `parent_discovery_artifact_id` 与 `refinement_request`；不要手写完整 discovery。

## 分层阶段图

读取用户确认的 flow，再查询并回读主调用链。按“用户动作 → 业务大阶段 → 可定位子阶段 → 函数实现”建模。`@stage` 是后续可单独寻找 HiTrace 边界的子阶段；一个实现边界对应一个清楚的阶段语义。

只生成 Mermaid，并调用 `application_flow_compile_mermaid`。每个 stage 配置一个 hierarchy 绑定和至少一个已核对的 implementation；实现位于关联仓时，`@implementation` 增加 `source_connector_id`。工具把子阶段投影到稳定 `application-flow-scenario/v2`，缺少 Trace 时使用 `matcher: unavailable`。

用户修改已有场景时读取当前场景，只重查受影响部分。调用编译工具时传 `parent_scenario_artifact_id` 与原始 `revision_request`，形成可追溯的新版本。

## HiTrace 锚点

对每个 implementation 先调用 `application_flow_inspect_trace_instrumentation`，再按 stage 与相邻函数链补查。检查器覆盖直接 HiTrace API、模块宏、包装函数、RAII scope、ArkTS `Trace.*` 与 `hiTraceMeter.*`；沿 `wrapper_chain` 核对真正的 HiTrace 调用、参数传递和 start/end 语义。

字面量提交真实 label，格式化或模板事件提交静态前缀，`__func__/__PRETTY_FUNCTION__` 提交稳定 selector 并标记 `function_derived`。边界位于关联仓时提交 `source_connector_id`；携带仓内相对路径、行号、调用名和所在函数，找不到的一侧留空。一次调用 `application_flow_enrich_trace_anchors` 提交全部阶段。源码插桩只证明当前快照存在声明，真实运行、关键路径和耗时由后续 Trace 实例化确认。
