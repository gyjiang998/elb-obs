# Trace 热点代码深挖

目标是从 trace 边界找到“值得继续优化分析的最小代码候选”，不是把桩点所在函数自动宣布为热点。

1. 先校准时间语义：stage duration 是阶段包络；事件 duration 默认是 inclusive span。没有 Hiperf、CPU sample、嵌套 self-time 或等价证据时，不得给桩点函数或 callee 分配耗时、占比或排名。
2. 先定位原始 event label 对应的插桩行和包围函数。该函数只记为 `trace_anchor_function`；标签恰好像函数名，也不改变这一证据等级。
3. 使用后端原生代码工具和真实编译上下文，自适应检查：桩点覆盖的局部区域、直接 caller、直接 callee、必要的传递 callee、虚调用/函数指针目标，以及源码之外的 runtime/model/driver 边界。优先 Clang AST、CFG、compile_commands 和可复核调用点；缺失时用 `rg` 与精确源码行。不要固定调用深度。
4. 候选类型仅用于描述，不是结论：`local_region`、`callee_function`、`transitive_callee`、`caller_region`、`function_pointer_target`、`external_runtime_or_model_boundary`。
5. 独立比较四个维度：与 trace 边界的关联、该路径实际执行的可能性、源码中的成本信号、代码是否属于可优化范围。成本信号包括规则循环、批量访存、重计算库调用、分配/拷贝、锁/等待/IPC、硬件提交；普通日志、错误分支、getter 和薄 wrapper 默认降权。
6. 每条判断标明证据：`trace_observed`、`source_observed`、`model_hypothesis` 或 `unresolved`。源码存在只能证明代码内容；调用点存在只能证明静态关系；无采样时“它最热”仍是 `model_hypothesis_without_cpu_sampling`。
7. 若当前仓没有实现，保留 `external_runtime_or_model_boundary`，列出需要的 runtime 源码、模型图/算子 profile、调用栈或采样证据。不得用同名 wrapper、声明、服务代理或相邻代码代替实现。
8. 只有找到源码可观察的最小候选时，才调用 `reasoning.select_hotspot_source_candidate`，提交精确 path、行范围、candidate_kind、relation_to_anchor、rationale 和可复核 call_path。该 action 验证源码并回填页面，但不会把模型假设升级成采样事实。
9. 若没有可提交候选，停止在 `evidence_required`；不要继续硬件路由。若有多个合理分支，保留少量候选和区分它们所需的最小证据，不要强行单选。

面向用户用中文简洁说明：trace 证明了什么、源码证明了什么、模型推测了什么、最终选择了哪段代码或为什么没有选择。
