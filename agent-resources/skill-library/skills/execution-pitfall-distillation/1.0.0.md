# 执行踩坑提炼 Skill v1.0.0

目标：从历史对话、模型推理、工具调用和真机实验中提炼可复用的问题类与处置方案，解释不同模型、Agent 框架、宿主环境、SDK、代码仓和设备组合为何产生不同结果。

## 方法

1. 先调用 `experience_list_sources`，只选择与用户目标、失败阶段或对比环境相关的历史源；使用 `experience_read_source` 分批读取，不穷举全部历史。
2. 建立环境差异表，至少检查：模型及版本、Agent 框架及版本、Skill profile、宿主 OS/架构、代码仓与快照、SDK/编译器/runtime 库、设备型号、设备 OS 和连接拓扑。记录中没有的字段写“未知”，不得猜测。
3. 按“可观察症状 -> 真实错误或工具结果 -> 尝试动作 -> 动作后结果”重建证据链。Agent 自述、模型推测和错误信息中的归因都不是已证明根因。
4. 为每类问题生成稳定 `recurrence_key`。它描述可跨 Run 复用的问题机制，不包含 Run ID、设备序列号、临时路径、具体变量名或单次错误全文。
5. 区分问题归属：基础环境、SDK/工具链、runtime 库、代码仓、设备/OS、模型行为、Agent 框架、工作流、Skill 或证据合同。基础设施问题不要靠增加 Prompt 规则掩盖；单一样本不要写成通用 Skill 条款。
6. 每个问题给出 1-4 个可选择处置方案，明确由用户还是 Agent 执行、前置条件、风险与验证方法。可能的处置包括环境变量、代码仓、SDK/library、设备、Runtime Adapter、流程、代码或 Skill 版本。
7. 只有当失败来自可泛化的推理方法、工具选择或停止条件时，才建议 `skill_revision`。必须指出目标 Skill、泛化边界和至少一个正例/反例回归；不要把 corner case 原文直接追加进 Skill。
8. 调用 `experience_save_review` 保存结果。保存只形成候选，不自动修改环境、代码、知识库或 Skill。用户选择方案后，才使用对应工具执行并用 `experience_triage_case` 更新状态。

## 完成条件

- 每个踩坑都有历史源证据、根因置信度、适用范围和泛化边界。
- 环境差异中的未知项保持未知。
- 每个处置都可执行、可验证、可回退。
- 明确区分“已观察”“根因假设”“已选择”“已解决”和“已验证”。
